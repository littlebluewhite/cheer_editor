# iPhone、iPad app：殼自己從網站更新網頁，伺服器照樣只認同一份流程核心

伺服器只讓流程核心指紋完全一樣的人連進雲端流程（`server/src/flow_room.rs`）。核心改一行程式，指紋就換；推上 `main` 就部署。app 裡的網頁原本要等新版 app 過審（通常 1–2 天）、使用者按更新才換得到，這段時間 app 連不上雲端流程，也不能記。所以殼自己去網站抓新版網頁換上，像網頁重新整理一樣。伺服器不改，照樣只認完全一樣的指紋。

為什麼：照現在的比對，不管誰先換都有一邊被擋。伺服器先換，商店裡的舊 app 被擋；伺服器等 app 過審才換，審查期間 app 比伺服器新，審查的人連正式站（沒有測試站）一樣被擋。放寬比對要人手寫相容版號：忘了加 1，舊核心會悄悄丟掉看不懂的新東西（`src/lib/core/remote-change.ts` 只套認得的欄位）；以後每次改核心、房間訊息、API 都要顧舊 app。開工前 `main` 有進東西的 9 天，9 天都動到流程核心。

## Considered Options

- **殼自己從網站更新網頁（選這個）**：見上面。伺服器、指紋都不改；伺服器倒回舊版時 app 也跟著換回去。
- **伺服器放寬，用人手寫的相容版號**：沒有 Apple 的風險。可是要一直顧舊 app，忘了加 1 就悄悄丟東西。Apple 不准上面那條時，改走這條。
- **伺服器部署等 app 過審**：審查期間 app 比伺服器新，審查的人被擋；網頁也要跟著等；過審後還沒更新的人照樣被擋。

決定的細節在 #307。

## Consequences

- 什麼時候換：app 打開、回到前景時去網站看有沒有新版，有就在背景下載（整包約 3 MB）。下好了不馬上換，回到首頁或下次打開 app 才換。雲端流程被擋時，畫面寫「有新版」，加一個「更新」按鈕，按了馬上換，換完回到同一支流程。
- 比的是「跟網站上的一不一樣」，不比新舊。新的打不開就退回原本那包。只從自己的網站抓，照網站給的清單檢查每個檔。部署時網站要多放這份清單，伺服器的程式不改。
- 新網頁要用到殼的新功能時，先問殼會不會，不會就先不顯示那個功能。真的沒辦法在舊殼上跑，才標「要第幾版以上的殼」：舊殼不換網頁、照下一條被擋，畫面寫「這版 app 太舊，請到 App Store 更新」，加一個開 App Store 的按鈕。只有這時候，伺服器部署要等新版 app 過審、大家更新。
- 被擋的時候（app 和 Safari 一樣）：能看，照樣抓最新的給人看，不卡在舊的離線副本；能記，存著，更新後再傳（記到已經被刪掉的動作的那幾次，照樣丟掉，跟斷線時記的一樣）；不能改，也不能下載流程檔（會把新內容標成舊的格式版本）。本機流程照舊。
- 殼轉送網路（ADR 0019）是通用的：網頁連自己網站 `/api/` 底下的任何路徑都轉，只轉到自己的網站。伺服器加新的 API，不用出新版 app。
- app 只有殼改了才出新版，裡面那包網頁用出版那天的 `main`。從 App Store 裝一定有網路，第一次打開就會抓最新的。
- 送審備註寫清楚「app 會從自己的網站更新網頁畫面，功能不變」。Apple 準則 2.5.2 不准下載會改變功能的程式，授權合約 3.3.1(B) 准下載 JavaScript 這類程式、只要不改 app 的主要用途（本機分支 `research/app-store-rules`）。准不准是推論，沒驗。被退，或上架後被要求拿掉，就改走「伺服器放寬」。
- ADR 0018 的「網頁改了，要出新版 app 才拿得到」、ADR 0019 的「殼只開 app 裡那包網頁」跟著改了。
