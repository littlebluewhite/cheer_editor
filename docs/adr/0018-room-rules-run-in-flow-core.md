# 房間規則只有一份：Rust 伺服器用 QuickJS 叫流程核心的 `takeStep`

「這一步收不收」（收過的步驟 id、權限、前一步被退回、太久、復原的 30 天、改到同一個東西、被規則擋下、紀錄跟著清掉或加回來）寫在流程核心的 `takeStep`（`src/lib/core/room-step.ts`，#315），假伺服器叫它。#323 以前 Rust 伺服器另有一份（`flow_room.rs` 的 `take_step`，加上 `records.rs` 的 `brought_back`、`after_step`），兩份已經對不上過好幾次（e3ef238 修過一次重做；30 天前的步不能復原假伺服器沒抄）。

#308 階段 6 原本的門檻是「1 MB 的流程一步在 50 毫秒以內（ADR 0013 量到的範圍）才讓 Rust 改叫它」。量到 `takeStep` 插入一個八拍約 90 毫秒、復原約 155 毫秒，沒過；可是 #323 以前的伺服器自己也沒過（插入一個八拍約 101 毫秒、復原約 173 毫秒）。50 毫秒擋的是一條本來就不在的路，所以門檻改成「不比 #323 以前的伺服器慢」，`takeStep` 過了。

**決定：Rust 伺服器收一步（`server/src/flow_room.rs` 的 `take_step`）用 QuickJS 叫 `takeStepJson`（`src/lib/core/bundle-entry.ts`），收不收只看它的結果；Rust 裡自己的規則刪掉。** 指令、整份流程檢查、這一步收不收都只有一份 TypeScript（ADR 0013）。

## 為什麼門檻改了

- 50 毫秒來自 ADR 0013：整支含紀錄跑一個指令。紀錄分開存（ADR 0011）之後，伺服器每一步還要放回紀錄、拿出來、比對前後（`runStepJson` ＋ `remoteChangeJson`，兩次進出 QuickJS），本來就超過 50 毫秒（下表）。
- `takeStep` 一次做完，量到的不比 #323 以前慢：改名字約 45 對 56、插入一個八拍約 90–98 對 101、復原約 154–164 對 173（毫秒，中位數）。
- 教練好幾秒才做一步，一步 100–170 毫秒照樣夠用；兩份規則對不上才是會出錯的地方。

## 量的方法

- 測試：`server/src/flow_core.rs` 的 `room_step_timing`（平常不跑）。`cd server && cargo test --release --lib -- --ignored --nocapture room_step_timing`。
- 流程：`server/tests/fixtures/big-flow.js` 用流程核心的指令做：36 人、80 個動作（每個 3 個環節、兩組）、80 張站位、5,500 次紀錄。不帶紀錄的編排 139,760 bytes，紀錄 1,155,001 bytes，整支含紀錄 1,045,430 bytes（約 1 MB）。
- 三種步：改流程名字（幾乎只有 JSON 進出）、在最前面插入一個八拍（後面 80 個動作、80 張站位全部往後挪）、復原改名字。
- 步驟紀錄：0、100、1,000、5,000 筆（`takeStep` 要的是上次看到之後、和要復原的那一步之後的每一步，不先挑分頁、改到的東西）。每筆是別的分頁改了一個隊員，沒有清掉的紀錄。
- 從 Rust 傳 JSON 字串進 QuickJS、拿 JSON 字串回來，包含在時間裡。每種先跑 3 次暖身，再跑 25 次，記最快和中位數。每次都檢查結果是「收了」，不是早早退回。
- 機器：Apple M3 Max（16 核）、macOS，`--release`（rquickjs 0.14、rustc 1.98.1），2026-11-21。跑的時候這台機器同時在跑別的工作（load average 約 18–30），所以同一個量尺也跑一次比對（下表第一段）。數字只能看量級，不等於 Fly.io 機器上的數字。

## 收紀錄也改叫流程核心（#349，2026-11-22）

#348 把「這串紀錄收不收」寫成流程核心的 `receiveRecords`（假伺服器叫它）。#349 量了才讓 Rust 改叫，門檻同上：同一台機器、同一次跑，中位數不比 #349 以前的伺服器慢。**過了，Rust 改叫 `receiveRecordsJson`，Rust 裡自己的規則刪掉。**

**量的方法**

- 決定看的是整段（連 PostgreSQL）：`server/src/records_timing.rs` 的 `record_timing`（平常不跑）。`npm run test:server -- --release --lib record_timing -- --ignored --nocapture`。
- 只量 QuickJS 決定不了：整批都收過的重送 #349 以前根本不進 QuickJS（0 毫秒對大於 0），而且變的主要是 SQL（以前重送要讀整份紀錄；以前一次全上每筆查一次 SQL，現在一次挑完）。所以 #349 以前的 `record` 照抄在 `records_timing.rs`，只給量時間比，伺服器不叫；`FlowCore::check_records` 也只留給它。
- 流程同上（`big-flow.js`，編排 139,760 bytes，存著的紀錄 5,500 次，記的人都是空的），存在 `#[sqlx::test]` 開的資料庫裡。三種：一次送 1 筆（分段練，新的 id）；一次送 40 筆（一次全上，40 個不同的動作）；整批 40 筆都是收過的重送。
- 交錯量：每一對兩邊各跑一次、輪流先跑哪一個，3 對暖身不算；送 1 筆 1,001 對（兩邊差不到 0.2 毫秒，61 對看不出來），另外兩種 61 對。每次都確認全部收了（1 筆、40 筆都收、0 筆沒收；重送 40 筆回存著的），新增的在計時外刪掉。印兩邊的中位數、每對相減的中位數、幾對不比以前慢。
- 判斷照字面的門檻：每種情境、每次跑，改叫之後的中位數不比以前大。跑三次。
- 機器：Apple M3 Max（16 核）、macOS、`--release`，PostgreSQL 18 跑在 Docker（macOS 上每次查詢的來回比正式機慢，這對以前一次全上每筆查一次 SQL 不利，所以 40 筆的差距在正式機上可能小一點）。跑的時候這台機器同時在跑別的工作（load average 約 24–41）。

**量到的數字（毫秒，中位數；最後的做法，同一個指令跑三次）**

| 情境 | #349 以前 | 改叫流程核心 | 每對相減（改叫 − 以前） | 不比以前慢的對數 |
|---|---|---|---|---|
| 送 1 筆（1,001 對） | 8.28 / 4.05 / 3.76 | 7.97 / 4.00 / 3.75 | −0.06 / −0.02 / −0.02 | 522 / 520 / 520 |
| 送 40 筆（一次全上，61 對） | 15.79 / 18.82 / 17.73 | 12.42 / 14.96 / 14.11 | −3.17 / −3.27 / −3.18 | 61 / 52 / 56 |
| 整批 40 筆收過的重送（61 對） | 13.06 / 13.08 / 12.76 | 3.44 / 3.63 / 3.02 | −9.55 / −9.47 / −9.62 | 61 / 60 / 60 |

- 三次跑、三種情境，改叫之後的中位數都不比以前大：過了。
- 40 筆、重送每次都快：40 筆少了 40 次查同一組的 SQL；重送不再讀整份 5,500 次紀錄。
- 1 筆只是剛好過：中位數差 0.01–0.31 毫秒，每對相減約 −0.02 毫秒，大約一半的對比較快。等於一樣快，換一台機器可能翻過來。
- 過程（都是同一台機器、同一次跑交錯）：
  - 第一版把編排包在 ask 裡（Rust 要先用 `RawValue::from_string` 檢查一遍約 140 KB 的 JSON）。61 對時 1 筆三次跑都慢一點（6.00 對 6.21、3.61 對 3.91、3.94 對 4.06），照字面沒過；40 筆、重送就快了。
  - 改成編排另外一個參數（`receiveRecordsJson(flow, ask)`，存著的原樣傳）之後，61 對時 1 筆三次跑是 3.71 對 3.66、13.85 對 14.54、4.22 對 4.26（相減 −0.01、−0.20、+0.04），正負會換、分不出來，所以加到 1,001 對，得到上表。
- 只看 QuickJS 裡的時間（`room_step_timing` 最後三行，交錯 61 對）：`receiveRecordsJson` 三種都比較慢：1 筆 `checkRecordsJson` 1.53 對 1.59；40 筆 2.45 對 2.55；重送 0（以前不進 QuickJS）對 0.33（編排給 `null`）。多的不到 0.1 毫秒（重送 0.33），比省下的 SQL 少，所以整段沒有變慢。只量 QuickJS 決定不了這件事（重送一定是 0 對大於 0）。
- 在比較安靜的機器上再跑一次，如果 1 筆每次都慢，照字面的門檻就是沒過，要改走共用情境檔（見 #347 階段 A2）。

## Considered Options

- **Rust 改叫 `takeStep`，規則只有一份 TypeScript（選這個）**：門檻照「不比 #323 以前慢」過了。Rust 只剩挑資料、存、鎖、傳。
- **共用的情境檔（同一份 JSON 情境在 Vitest 跑假伺服器、在 cargo test 跑真的伺服器）**：#308 原本的 50 毫秒門檻沒過時的做法。規則還是兩份，靠情境對齊；情境沒寫到的地方照樣會對不上。不選。
- **維持現狀（兩份規則、沒有情境檔）**：已經對不上過好幾次。不要。

## Consequences

- `flow_room.rs` 的 `take_step` 做的：鎖住那一列（`FOR UPDATE`）；流程被刪了回 `Deleted`、權限被收回回 `Revoked`；用 SQL 挑出 `takeStep` 要的傳進去：
  - 現在的編排（存著的 JSON 原樣）和第幾步；
  - 這支流程的紀錄，照存的先後，連清掉的（`gone`）和 `amended_step`（`records.rs` 的 `for_room`）；
  - 步驟紀錄：上次看到之後的每一步，復原、重做時再加上要復原的那一步和它之後的每一步（每筆的步驟 id、分頁、名字、時間、改到的東西、清掉的紀錄）；30 天的規則在 `takeStep`，SQL 不先挑；
  - 這個步驟 id 收過了：那一步第幾步、那一步的改動（這時紀錄、步驟紀錄給空的，不讀）；
  - 權限（能不能改）、這個分頁、送的人的名字、這個連線上次被退回時第幾步、現在的時間。
- 結果照 `kind`：收過的回 `Accepted`；退回的原因（代號）原樣變成 `SentBack`，Rust 寫上中文句子（`message`）；收了的存起來：編排、第幾步、步驟紀錄（改到的東西、改動、清掉改掉的紀錄），紀錄照 `takeStep` 給的先後清掉、改掉（`records.rs` 的 `store_step`），再記下音樂哪天不用了。
- 留在 Rust 的：用 SQL 挑步驟紀錄和紀錄、存、鎖、流程被刪了、權限被收回、退回和沒收的中文句子、音樂哪天不用了、送給房間裡的人。房間的訊息、`src/lib/api-types/`、migration 都沒變。
- 收紀錄（`records.rs` 的 `record`，#349）也一樣：鎖住那一列、流程被刪了回 `Deleted`、權限被收回回 `Revoked`；用 SQL 只挑有關的紀錄（同樣 id 的連清掉的、同一次全上還在的，帶記的人的名字），不讀整份紀錄；送的人的名字在鎖裡先拿；叫一次 `receiveRecordsJson`（整批都收過時編排給 `null`）；照結果存、寫沒收的中文句子（「你只能看這支流程」「某某已經記了這次全上的這一組」、流程核心給的原因、「伺服器看不懂這一筆」）、告訴房間裡的人。同一批重複的 id、收過的 id、檢視者、「記一次」的檢查、同一次全上的同一組，都只在 `receiveRecords`（`room-records.ts`）。流程核心自己丟例外時，送來的每一筆都當「伺服器看不懂這一筆」，並記一行 warn。
- 改、刪、救回（`records.rs` 的 `amend`）還是 Rust 自己的規則（#347 階段 A3 再量）。
- 改房間規則只改 `takeStep`（和 `room-step.test.ts`）；改收紀錄的規則只改 `receiveRecords`（和 `room-records.test.ts`）。Rust 的情境測試（`server/tests/` 的 `flow_steps`、`cloud_undo`、`same_thing`、`records`、`room_live`）照舊跑真的伺服器，管挑資料、存、鎖、傳有沒有接對。
- 流程核心自己丟例外（不是 `takeStep` 退回的）：Rust 當「伺服器看不懂這一步」退回，並記一行 warn。
- `runUndoJson` 伺服器不再叫，只留給 `room_step_timing` 量 #323 以前的做法。以後流程核心變慢、或流程變大，用同一個測試再量，跟上表比。
- 上表 `takeStepJson` 的數字只有 QuickJS 裡的時間；接上之後 Rust 用 SQL 挑資料的時間沒有重量。比 #323 以前多讀的：每一步都讀清掉的紀錄（以前只有復原才讀）和上次看到之後的每一筆步驟紀錄（以前是只拿一筆的查詢）。檢視者、前一步被退回、太久以前在叫流程核心之前就回了，現在也要挑完資料、進一次 QuickJS 才回。收過的步驟 id（斷線重送）不讀紀錄和步驟紀錄（給空的，`takeStep` 先看 `taken`，用不到它們），可是還是要進一次 QuickJS（傳現在的編排）才回。
- 每一步都讀這支流程的全部紀錄，連清掉的。沒有東西會刪掉 `flow_records` 裡清掉的紀錄（`daily.rs` 每天只刪 `flow_steps`），所以這一步會越讀越多；這件事沒有量過（上表的 5,000 筆步驟紀錄、5,500 次紀錄都沒有清掉的）。
- 上次看到的步（`seen`）很舊的話，要先讀完那之後的每一筆步驟紀錄，`takeStep` 才回「太久」。
