# 房間規則只有一份：Rust 伺服器用 QuickJS 叫流程核心的 `takeStep`

「這一步收不收」（收過的步驟 id、權限、前一步被退回、太久、復原的 30 天、改到同一個東西、被規則擋下、紀錄跟著清掉或加回來）寫在流程核心的 `takeStep`（`src/lib/core/room-step.ts`，#315），假伺服器叫它。#323 以前 Rust 伺服器另有一份（`flow_room.rs` 的 `take_step`，加上 `records.rs` 的 `brought_back`、`after_step`），兩份已經對不上過好幾次（e3ef238 修過一次重做；30 天前的步不能復原假伺服器沒抄）。

#308 階段 6 原本的門檻是「1 MB 的流程一步在 50 毫秒以內（ADR 0013 量到的範圍）才讓 Rust 改叫它」。量到 `takeStep` 插入一個八拍約 90 毫秒、復原約 155 毫秒，沒過；可是 #323 以前的伺服器自己也沒過（插入一個八拍約 101 毫秒、復原約 173 毫秒）。50 毫秒擋的是一條本來就不在的路，所以門檻改成「不比 #323 以前的伺服器慢」，`takeStep` 過了。

**決定：Rust 伺服器收一步（`server/src/flow_room.rs` 的 `take_step`）用 QuickJS 叫 `takeStepJson`（`src/lib/core/bundle-entry.ts`），收不收只看它的結果；Rust 裡自己的規則刪掉。** 指令、整份流程檢查、這一步收不收都只有一份 TypeScript（ADR 0013）。

## 為什麼門檻改了

- 50 毫秒來自 ADR 0013：整支含紀錄跑一個指令。紀錄分開存（ADR 0011）之後，伺服器每一步還要放回紀錄、拿出來、比對前後（`runStepJson` ＋ `remoteChangeJson`，兩次進出 QuickJS），本來就超過 50 毫秒（下表）。
- `takeStep` 一次做完，量到的不比 #323 以前慢：改名字約 45 對 56、插入一個八拍約 90–98 對 101、復原約 154–164 對 173（毫秒，中位數）。
- 教練好幾秒才做一步，一步 100–170 毫秒照樣夠用；兩份規則對不上才是會出錯的地方。

## 量的方法

- 測試：`server/src/flow_core.rs` 的 `room_step_timing`（平常不跑）。`cd server && cargo test --release --lib -- --ignored --nocapture room_step_timing`。
- 流程：`server/tests/fixtures/big-flow.js` 用流程核心的指令做：36 人、80 個動作（每個 3 個環節、兩組）、80 張站位、5,500 次紀錄。不帶紀錄的編排 139,760 bytes，紀錄 1,155,001 bytes，整支含紀錄 1,045,430 bytes（約 1 MB）。
- 三種步：改流程名字（幾乎只有 JSON 進出）、在最前面插入一個八拍（後面 80 個動作、80 張站位全部往後挪）、復原改名字。
- 步驟紀錄：0、100、1,000、5,000 筆（`takeStep` 要的是上次看到之後、和要復原的那一步之後的每一步，不先挑分頁、改到的東西）。每筆是別的分頁改了一個隊員，沒有清掉的紀錄。
- 從 Rust 傳 JSON 字串進 QuickJS、拿 JSON 字串回來，包含在時間裡。每種先跑 3 次暖身，再跑 25 次，記最快和中位數。每次都檢查結果是「收了」，不是早早退回。
- 機器：Apple M3 Max（16 核）、macOS，`--release`（rquickjs 0.14、rustc 1.98.1），2026-11-21。跑的時候這台機器同時在跑別的工作（load average 約 18–30），所以同一個量尺也跑一次比對（下表第一段）。數字只能看量級，不等於 Fly.io 機器上的數字。

- 量尺改名字跟 ADR 0013 當時一樣（23 毫秒），插入一個八拍多約 1.3 倍（當時 52）。就算把 `takeStep` 的數字都除以 1.3，插入一個八拍（約 70）、復原（約 120）還是超過 50 毫秒：不是機器忙造成的。
- 步驟紀錄多少幾乎不影響（0 到 5,000 筆差不到 10 毫秒）。時間花在把約 1 MB 的流程和紀錄傳進傳出、放回紀錄再拿出來、比對前後，和復原的整份流程檢查。

## Considered Options

- **Rust 改叫 `takeStep`，規則只有一份 TypeScript（選這個）**：門檻照「不比 #323 以前慢」過了。Rust 只剩挑資料、存、鎖、傳。
- **共用的情境檔（同一份 JSON 情境在 Vitest 跑假伺服器、在 cargo test 跑真的伺服器）**：#308 原本的 50 毫秒門檻沒過時的做法。規則還是兩份，靠情境對齊；情境沒寫到的地方照樣會對不上。不選。
- **維持現狀（兩份規則、沒有情境檔）**：已經對不上過好幾次。不要。

## Consequences

- `flow_room.rs` 的 `take_step` 做的：鎖住那一列（`FOR UPDATE`）；流程被刪了回 `Deleted`、權限被收回回 `Revoked`；用 SQL 挑出 `takeStep` 要的傳進去：
  - 現在的編排（存著的 JSON 原樣）和第幾步；
  - 這支流程的紀錄，照存的先後，連清掉的（`gone`）和 `amended_step`（`records.rs` 的 `for_room`）；
  - 步驟紀錄：上次看到之後的每一步，復原、重做時再加上要復原的那一步和它之後的每一步（每筆的步驟 id、分頁、名字、時間、改到的東西、清掉的紀錄）；30 天的規則在 `takeStep`，SQL 不先挑；
  - 這個步驟 id 收過了：那一步第幾步、那一步的改動；
  - 權限（能不能改）、這個分頁、送的人的名字、這個連線上次被退回時第幾步、現在的時間。
- 結果照 `kind`：收過的回 `Accepted`；退回的原因（代號）原樣變成 `SentBack`，Rust 寫上中文句子（`message`）；收了的存起來：編排、第幾步、步驟紀錄（改到的東西、改動、清掉改掉的紀錄），紀錄照 `takeStep` 給的先後清掉、改掉（`records.rs` 的 `store_step`），再記下音樂哪天不用了。
- 留在 Rust 的：用 SQL 挑步驟紀錄和紀錄、存、鎖、流程被刪了、權限被收回、退回的中文句子、音樂哪天不用了、送給房間裡的人。房間的訊息、`src/lib/api-types/`、migration 都沒變。
- 改房間規則只改 `takeStep`（和 `room-step.test.ts`）。Rust 的情境測試（`server/tests/` 的 `flow_steps`、`cloud_undo`、`same_thing`、`records`、`room_live`）照舊跑真的伺服器，管挑資料、存、鎖、傳有沒有接對。
- 流程核心自己丟例外（不是 `takeStep` 退回的）：Rust 當「伺服器看不懂這一步」退回，並記一行 warn。
- `runUndoJson` 伺服器不再叫，只留給 `room_step_timing` 量 #323 以前的做法。以後流程核心變慢、或流程變大，用同一個測試再量，跟上表比。
- 上表 `takeStepJson` 的數字只有 QuickJS 裡的時間；接上之後 Rust 用 SQL 挑資料的時間沒有重量。比 #323 以前多讀的：每一步都讀清掉的紀錄（以前只有復原才讀）和上次看到之後的每一筆步驟紀錄（以前是只拿一筆的查詢）。收過的步驟 id、檢視者、前一步被退回、太久以前在叫流程核心之前就回了，現在也要挑完資料、進一次 QuickJS 才回。
- 每一步都讀這支流程的全部紀錄，連清掉的。沒有東西會刪掉 `flow_records` 裡清掉的紀錄（`daily.rs` 每天只刪 `flow_steps`），所以這一步會越讀越多；這件事沒有量過（上表的 5,000 筆步驟紀錄、5,500 次紀錄都沒有清掉的）。
- 上次看到的步（`seen`）很舊的話，要先讀完那之後的每一筆步驟紀錄，`takeStep` 才回「太久」。
