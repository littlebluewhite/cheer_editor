# 伺服器用 QuickJS 跑同一份 TypeScript 流程核心

伺服器要知道流程的規則：每一步套上去之前要檢查（ADR 0007），收到成功率紀錄也要用同一套「記一次」的規則檢查（ADR 0008）。這些規則寫在 TypeScript 的流程核心（`src/lib/core/`），指令會用到的部分約 3,400 行程式、53 個指令。所以不另寫一份：把流程核心打包成一個 JS 檔，在 Rust 伺服器裡嵌一個小的 JS 引擎 QuickJS（`rquickjs`）來跑。規則只有一份，前端和伺服器跑的是同一份，結果一定一樣。

## Considered Options

- **QuickJS 跑同一份 TypeScript（選這個）**：執行檔只多約 1.7 MB，記憶體很少。實測輸出跟 Node 逐位元組一樣。1 MB 的流程一步約 25–50 毫秒（本機實測），教練好幾秒才做一步，夠用。缺 `Intl.Segmenter`，要補一個由 Rust（`unicode-segmentation`）切字的小墊片。
- **V8（`deno_core`）**：不用補、快約 5 倍。可是執行檔約 60 MB，建置時要下載約 39 MB 的 V8，記憶體也多，我們的機器只有 512 MB。
- **旁邊另開一個 Node／Bun 程序**：不用補就能跑。可是多一個程序要顧，程序之間傳 1 MB 的流程要自己處理，一不小心會卡住。
- **用 Rust 重寫規則**：伺服器全是 Rust、跑得快。可是要寫約 3,400 行程式和約 7,500 行測試，以後每改一條規則都要改兩份、一直對齊。
- **規則用 Rust 寫一份，編成 WebAssembly 給前端用**：一樣只有一份。可是要先全部重寫，前端 41 個檔要改呼叫方式，建前端也要裝 Rust。
- **規則只放伺服器，前端每一步都去問**：本機流程斷網就不能改，也不能先改自己的畫面（ADR 0007）。不行。

研究筆記：`research/run-ts-core-on-server` 分支的 `docs/research/run-ts-core-on-server.md`。決定的細節在 #188。

## Consequences

- 前端送的一步是「指令名字＋參數」，伺服器拿同一個指令再跑一次。
- 指令一定要同樣的輸入給同樣的結果。新東西的 id 由前端發好，當參數送（ADR 0007 要改成不會撞的 id）；核心裡不能用現在的時間或亂數（現在也沒用）。
- 「檢查一整支流程」（`isFlow`、舊版升級）現在包在 `readFlowFile` 裡，要拆出來單獨匯出，傳上雲端時伺服器才用得到。
- 打包要選瀏覽器版的依賴（例：rolldown、esbuild 用 `--platform neutral`），不然 `fflate` 會帶進 Node 才有的東西。
- QuickJS 的 runtime 不能跨執行緒。伺服器開一條專用執行緒擁有它，一步一步排隊處理；ADR 0007 本來就照收到的先後套。
- 伺服器切字用的 Unicode 版本跟各家瀏覽器可能不同，極少數很新的 emoji，前後端算出來的字數可能差一個。
