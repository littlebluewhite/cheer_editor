# 一起記全上的表也由流程核心算：兩個門檻都過了，Rust 下一張改叫它

一起記全上的表（誰在哪次全上的表裡、誰拿著哪幾組、點過沒，ADR 0015）怎麼變，#352 以前寫了兩份：Rust 伺服器的 `server/src/run_together.rs`，和假伺服器手抄的一段（`src/lib/test-fakes.ts`）。手抄的那段已經跟真的不一樣：沒有「斷線 1 分鐘當他離開」、被收回或降成檢視者時沒請出表、點組和放掉也會把人加進表裡、表沒變也照樣告訴大家、沒人連著了表也還在。

#352 把規則寫成流程核心的 `runTogether`、`runViews`（`src/lib/core/run-together.ts`），規則照 `run_together.rs` 一行一行搬，假伺服器改叫它，手抄的那段刪掉。前端測試的期望一個都沒改（`npm test` 照舊全過）。表照舊只放伺服器的記憶體（ADR 0015）；真正擋住「一組記兩次」的照舊是存紀錄（`receiveRecords`）和資料庫。

Rust 要不要也改叫，#347 訂了兩個門檻（規格訂的，不是量出來的），兩個都過才改叫：

1. 自己的時間：10 個人、40 組的表，「拿一組」加上給 10 個人看的樣子，在伺服器的 QuickJS 裡中位數 2 毫秒以內。
2. 排隊的時間：伺服器的 QuickJS 是所有流程共用一條執行緒、一次跑一件（`flow_core.rs`）。#352 以前拿一組在 Rust 裡做，不用排。前面排著一個約 1 MB 流程的插入八拍時，拿一組從交出去到拿回來，中位數 250 毫秒以內。

**決定：兩個都過了。下一張（#353）讓 Rust 伺服器把表照流程核心給的樣子放在房間的記憶體，每件事（開、加入、重報、拿、放掉、點了、離開、斷線、請出去）叫一次 `runTogetherJson`，把結果送出去；`run_together.rs` 裡自己的規則刪掉。** 不做共用的情境檔。

## 量的方法

- 測試：`server/src/flow_core.rs` 的 `run_together_timing`（平常不跑，不用 PostgreSQL）：`cd server && cargo test --release --lib run_together_timing -- --ignored --nocapture`。
- JSON 版入口 `runTogetherJson(runs, event)`（`src/lib/core/bundle-entry.ts`）：`runs` 是現在的表（Rust 原樣存著的 JSON），`event` 是那件事，多帶 `now` 和 `viewers`（要給哪些人看）。一次進出 QuickJS 就回新的表、回答、表變了沒、每個人看到的樣子。量的是這個形狀：一件事加 10 個人的樣子只進一次 QuickJS（排隊是照件數算的，分 11 次叫會多排 10 次）。
- 表：10 個人在同一次全上的表裡（第 1 個開、其他 9 個加入），每人拿 4 組、點過其中 2 組，共 39 組有人拿著；第 10 個人拿沒人拿著的第 40 組。表的 JSON 2,314 bytes，那件事 186 bytes。每次都確認拿到了（`done`）、回了 10 個人的樣子、表裡 10 個人、40 組。每次都從同一張表開始（拿之前的樣子）。
- 自己的時間：在跑流程核心的執行緒裡叫 `runTogetherJson`，JSON 字串進出包含在內，不算排隊、不算換執行緒。3 次暖身，再量 1,000 次。另外量一次從 Rust 交出去到拿回來（前面沒排別的，多了換執行緒），200 次。
- 排隊的時間：用真的 `FlowCore::start()`（伺服器用的同一條執行緒）。先交一個插入八拍（`take_step`，交的時候就排進隊伍），馬上交拿一組，量拿一組從交出去到拿回來。插入八拍用 `big-flow.js`（ADR 0018 的那支：不帶紀錄的編排 139,760 bytes，紀錄 5,500 次，整支約 1 MB），步驟紀錄 0 筆，在最前面插入一個八拍；每次都確認插入八拍收了、拿一組拿到了。3 次暖身，再量 25 次。同一次跑也量插入八拍自己（交出去到拿回來）當量尺。
- 拿一組的時鐘在插入八拍交出去之後才開始，插入八拍可能已經開始跑了一點，所以排隊的時間可能比插入八拍自己還短一點。
- 機器：Apple M3 Max（16 核）、macOS、`--release`（rquickjs 0.14、rustc 1.98.1），2026-11-22。跑的時候這台機器同時在跑別的 agent 的測試（load average 約 28–49，下表每次跑前後都記了）。數字只能看量級，不等於 Fly.io 機器上的數字。

- 自己的時間約 1 毫秒，是門檻的一半；不在「差 30% 以內」的邊上（1.4–2.6）。最慢的幾次超過 2 毫秒，是機器忙（中位數不受影響）。
- 排隊的時間約 90 毫秒，就是前面那個插入八拍的時間（拿一組自己只多約 1 毫秒）；離 250 很遠，不在邊上（175–325）。最慢的一次 289.5 毫秒，同一次跑的插入八拍自己最慢也到 188：是機器忙。
- 寫程式時先跑的一次（load average 約 49）：自己的時間中位數 0.961、排隊的時間中位數 91.3，跟上表一樣。

## 沒量到的

- 前面排著不只一件：好幾支流程同時有人在改、或復原一次加回 5,500 次（ADR 0018 量到約 200 毫秒）排在前面，拿一組就要等它們全部做完。#352 以前拿一組完全不用排；改叫之後，拿一組被晚一點回的時間就是前面排著的時間。教練點一組等 0.1–0.3 秒照樣夠用；一起記全上時最常見的是好幾個人點組，那些都只要約 1 毫秒。
- 斷線 1 分鐘後再說一次、每個連線把結果送出去的時間：這些照舊在 Rust 裡，沒量。
- 正式機（Fly.io）上的數字。

## Considered Options

- **Rust 改叫 `runTogetherJson`，規則只有一份 TypeScript（選這個）**：兩個門檻都過了。跟 ADR 0018 的收一步、收紀錄、改刪救回一樣，Rust 只剩放在記憶體、鎖、送。
- **共用的情境檔（同一份 JSON 情境在 Vitest 跑流程核心那組函式、在 Rust 的單元測試跑 `run_together.rs`）**：有一個門檻沒過時的做法。規則還是兩份，情境沒寫到的地方照樣會對不上。不選。
- **維持現狀（兩份）**：假伺服器已經對不上（見上）。不要。

## Consequences

- `runTogether(runs, event, now)` 做一件事，回新的表、要跟送的人說的（好了、拿不到和誰拿著、加入不了）、表變了沒；`runViews(runs, viewer, now)` 回給某一個人看的樣子（跟伺服器的 `RunView` 同一個型別，`run-together.test.ts` 用 `expectTypeOf` 對）。表是純 JSON：人用使用者 id、連線用號碼、時間用毫秒。
- 假伺服器跟真的一樣：表沒變不告訴大家；一個連線斷了（斷線、關掉）記下斷線的時間、1 分鐘後再說一次；被收回、降成檢視者時，他有開著的房間就請出每張表；這支流程沒有連著的房間了，表就沒了（真的伺服器拿掉房間）；斷線連回來是新的連線號碼。測試用假時鐘撥（`Date.now()`、`setTimeout`）。
- 規則測試在 `src/lib/core/run-together.test.ts`（表格，時間用給的），假伺服器接線測試在 `src/lib/fake-server-run-together.test.ts`。Rust 的 `server/tests/run_together.rs` 照舊跑真的伺服器。
- #353 改叫之後，`run_together.rs` 只留：把表（`runTogether` 給的 JSON）放在房間裡、誰送的（使用者 id、連線號碼、名字）、現在的時間、斷線 1 分鐘後再說一次、檢視者送的不收、把回答變成 `ClaimRefused`、`RunClosed`、把每個人的樣子變成 `RunThroughs` 送出去。房間的訊息、`src/lib/api-types/` 不變。ADR 0018「留在 Rust 的」那一段到時一起更新。
- 改叫之後，一起記全上的每件事都要排進流程核心的那條執行緒（上面「沒量到的」）。以後如果覺得點組變慢，用同一個測試再量。
