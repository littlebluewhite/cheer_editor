# 雲端上成功率紀錄跟編排分開存，一次一筆

流程檔裡，紀錄放在動作的成功率設定裡（`successRate.records`），跟編排存在同一份。雲端流程不這樣放：編排一份（環節和組還在裡面），紀錄另外一筆一筆存，一筆就是一次，指到它的動作、組（或隊員）和環節。下載成 zip 時再把紀錄放回流程檔，跟現在一樣。

原因：照 ADR 0007，改雲端流程是一步一步送、改到同一個東西時後到的退回，而且一定要有網路。紀錄如果留在流程裡，記一次就是改一次那個動作：記的人會跟正在改那個動作的教練互相退回；斷網時也不能記，但場館網路不穩，記成功率一定要能先記在手機上、有網路再傳。記錄者不能改流程，紀錄留在流程裡，伺服器還要另外分辨哪些修改只碰到紀錄。紀錄一年可能有幾萬筆，整份傳也太大。

## Considered Options

- **分開存，一次一筆（選這個）**：好幾個人同時記不會互相擋，也不會擋到改流程的人。每一筆在手機上就發一個不會撞的 id，重傳不會變兩筆。
- **留在流程裡（現在流程檔的樣子）**：格式不用改。但記一次就算改流程，會撞到 ADR 0007 的退回規則，斷網不能記。
- **CRDT（例：Yjs、Loro 的列表）**：會自動合併。可是紀錄只是一筆一筆往後加，分開存就有一樣的效果；CRDT 不管權限，還要多一個套件。

研究筆記：`research/concurrent-editing` 分支的 `docs/research/concurrent-editing.md`（#179）。決定的細節在 #186。

## Consequences

- 一次的 id 和全上的 id 不能再從流程依序發號（`t1`、`r1`…），兩支手機斷網各記一筆會撞號；改成手機發的、不會撞的 id，流程檔的格式要跟著改。
- 紀錄指到的環節、組、動作被教練刪掉後，才傳上來的紀錄照現在的規則處理：打在不在的環節上的記號丟掉，丟光或指到的動作、組、隊員不在了就整筆不存，手機上列出沒存進去的那幾筆。伺服器要跟流程核心用同一套「記一次」的規則檢查。
- 每一筆記下是誰記的（記錄者只能改、刪自己記的）。下載成 zip 不帶記的人；zip 傳上去以後，那些紀錄沒有記的人，只有編輯者、擁有者能改、刪。
- 改、刪紀錄可以斷網做；同一筆兩個人都改，後送到的贏，刪掉的不會被晚到的加回來。紀錄不像流程的一步會被退回。
